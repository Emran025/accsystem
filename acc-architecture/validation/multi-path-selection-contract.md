# عقد اختيار المسارات متعددة البدائل

## الغرض والحدود

يعرّف هذا العقد كيف يُمثَّل اختيار المسار في السجل المعماري، وكيف يفشل المحدد المرجعي عند غياب الاختيار أو أهليته أو أدلته. ملف `multi-path-readiness-register.json` هو مصدر القائمة، و`multi_path_selector_reference.py` نموذج تحقق معماري فقط؛ لا يمثل كوداً في ACCSystem ولا يثبت تشغيل أي مسار.

لا يختار هذا النموذج سياسة أو جهة مزوّد أو نقطة مالية نيابةً عن المالك. ولا يحوّل `RUNTIME_SELECTABLE` إلى موافقة أو قبول أو جاهزية `strict-ready`. كل بوابة مستقلة في `separate_gates` تظل مطلوبة بدليلها وسلطتها، كما تبقى متطلبات المصدر، والأمن، والملكية، وثوابت الحالة وidempotency، والأدلة الخارجية كما هي.

## كيف يعمل عقد الاختيار

لكل نطاق اختيار، يحدد العقد مستوى الاختيار من السياق الذي تسنده المصادر (`organization` أو `workflow` أو `transaction` أو `operation` أو `interface` أو `deployment`)، وأبعاده، ووضع الحل (`APPROVED_CONFIGURATION` أو `POLICY_AND_CAPABILITY` أو `CONDITION_BASED` أو `EVIDENCE_DRIVEN_CONFIGURATION`)، وقائمة السماح الدقيقة للمسارات. ترتبط كل خانة سماح بسلوك المسار وشروط النطاق من السجل نفسه، ومعرّفات المتطلبات والعقد المشترك، ومصفوفة انطباق معايير القبول، والبوابات المستقلة.

حدّ الاختيار تعاقدي معماري، وليس اسم حقل أو endpoint أو schema إنتاجي. لا تُنشأ قيمة selector أو precedence أو مدة أو default لا تدعمها المصادر. عند غياب اختيار صريح، لا يستنتج النموذج مساراً من مجرد كونه متاحاً؛ يسمح بالمسار الافتراضي فقط إذا كان المصدر يسميه، وكانت أهليته وبواباته وأدلته مستقلةً مستوفاة. أما الافتراضي الجزئي—مثل تفضيل اتجاه outbound مع ترك آلية الاتصال مفتوحة—فلا يختار آلية بعينها. وفي `CONDITION_BASED` لا يحسم النموذج إلا إذا أثبت السياق شرطاً مصدرّياً واحداً غير ملتبس؛ تعدد المسارات المؤهلة يوقف الاختيار.

المسار غير المؤهل لا يؤدي إلى fallback صامت. وإذا تعارضت سياسات معاملات، لا يجزّئ النموذج تلقائياً: يسمح بالتقسيم فقط عندما يذكره المصدر، وإلا يحجب القرار. يستخدم مرجع الاختيار سجلّات أدلة خارجية لكل بوابة، ومرجعاً لقرار/شرط الاختيار؛ هذه مدخلات للنموذج المرجعي وليست schema إنتاجياً أو ادعاءً بأن الدليل صحيح.

## معايير القبول والتنفيذ

كل معيار مصدرّي يظهر مرة واحدة في `acceptance_criteria_applicability`، مع فئة توضح هل ينطبق على العقد المشترك أو مجموعة مسارات محددة أو مسار inbound المحكوم بالموافقة أو سيناريو عابر للمسارات. يكرر `paths[*].acceptance_criteria` المعايير المنطبقة على ذلك المسار فقط. تظل كل الحالات `PLANNED_OR_SOURCE_DEFINED_NOT_EXECUTED`؛ إدراج معيار أو نجاح اختبار النموذج لا يعني اختبار قبول وظيفياً.

في `ADR-015-GATE` و`ODEC-001`، معيار outbound/firewall يخص مسارات outbound، ومعيار موافقة inbound يخص مسار inbound، بينما اختبار «كلا نمطي الاتصال» سيناريو نطاقي مخطط. معيار outbound لا يثبت الاختيار بين polling وlong-polling وpersistent channel. تبقى آليات القناة الثلاث خيارات تشغيلية مسماة بالمصدر من دون تفضيل مصطنع بينها.

## تصحيحات نطاقات محددة

- **`ODEC-001`:** يظل مسارَا الاتصال outbound وprotected inbound هما بديلَي الاتصال. نُقل وصف الاستضافة والتغليف من المسار الثالث إلى `orthogonal_configuration_dimensions` مع الاحتفاظ بنص المصدر ومعايير الاتصال التي كانت ملحقة به، ووسمها صراحة بأنها لا تثبت قبول الاستضافة/التغليف. المصدر لا يثبت مصفوفة توافق أو ترتيباً بين on-premises/public cloud وintegrated/separate apps؛ لذلك لم يُنشأ cross-product ولا معرّف متطلب جديد.
- **`RP-04` / `FinancialCommitment`:** بقي وصف البديل في `deferred_paths` وبحالة `DEFERRED_NOT_SELECTABLE`؛ يتطلب ADR مستقبلياً قبل اعتباره خياراً قابلاً للاختيار. المساران الحاليان لـ`OrderConfirmed` فقط في allowlist.
- **`RP-16`:** بقيت الحالة `DESIGN_REVIEW_REQUIRED` بسبب اختلاف تتبع 12 صفاً في السجل مقابل 3 في المراجعة. نقلت عبارة أن API keys غير مسموح بها من خانة المسار إلى `excluded_source_options`؛ OAuth 2.0 Client Credentials وmTLS هما المساران المصدرّيان، ولا يختار النموذج أحدهما في ظل تعارض التتبع.
- **مصادقة ADR-015:** يختار إعداد المؤسسة الطريقة المعتمدة بين OAuth 2.0 Client Credentials وmTLS؛ لا يوجد default أو precedence أو fallback بينهما. لا يخلط هذا العقد طريقة المصادقة باتجاه الاتصال أو آلية القناة أو إصدار المخطط.

## نتيجة العدّ من السجل

أعاد المدقق حساب **37 مرجعاً متعدد المسارات و41 نطاقاً**: 40 نطاقاً `RUNTIME_SELECTABLE` تصميمياً، و0 `IMPLEMENTED_MULTI_PATH`، ونطاق `RP-16` واحد `DESIGN_REVIEW_REQUIRED`. لكل نطاق من الأربعين عقد محدد منظم مكتمل وفق قواعد المدقق. تحتوي هذه النطاقات على 101 خانة مسار مسموح حالياً؛ وخارجها يوجد مسار مالي واحد مؤجل، وبُعد إعداد متعامد واحد، وعبارة استبعاد مصدرية واحدة. هذه أعداد سجل التصميم وليست عدد تطبيقات أو اختبارات مقبولة.

بوابة المتطلبات مستقلة ولم تتغير: `strict-ready` يبقى **835 ظهور predicate متداخلاً على 268 متطلباً نشطاً**، مع استمرار رمز الفشل. لم تُغيّر حالات المتطلبات أو القرارات أو الموافقات، ولم تُضف `PH-05` أو `ACCEPTED` أو `IMPLEMENTATION_READY`.

## التحقق

شغّل من جذر المستودع:

```bash
python3 acc-architecture/validation/validate_multi_path_readiness.py
python3 -m unittest acc-architecture/execution-phases/tests/test_multi_path_readiness.py -v
python3 acc-architecture/execution-phases/validate_requirements.py --check --strict-ready --summary
```

المدقق متعدد المسارات يثبت اتساق التصميم والتتبع فقط. يجب أن تبقى بوابة `strict-ready` مستقلةً وفاشلةً ما دامت موانعها قائمة؛ لا يسمح لهذا العقد أو للنموذج المرجعي بتغيير نتيجة تلك البوابة.
