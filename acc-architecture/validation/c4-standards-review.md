# C4 and Distributed-Architecture Review

**Review date:** 2026-11-19  
**Evidence base:** supplied ACC architecture ZIP, registry-first inventory, and three independent architecture reviews. This is a documentation review. It does not establish production implementation, owner approval, legal/security approval, or formal certification.

## C4 model

The original C4 model uses a system-context diagram to show one software system with the people and other software systems that directly interact with it. It is a high-level view, not a technology or protocol diagram. [1] A container diagram zooms into one software system and shows its applications/data stores, the way responsibility is distributed, technology choices, and how containers communicate. Its supporting elements are people and software systems directly connected to those containers. [2] A component diagram has one container as its scope and shows its components and responsibilities, with connected containers, people, and systems as supporting context. Component diagrams are optional when they do not add value. [3]

These are model definitions and recommendations, not a formal certification scheme. Mermaid syntax does not itself enforce C4 semantics. ACC's labels such as `COMPLETE`, its registry/matrix status rules, and its choice to group C2 views are local documentation conventions, not original C4 requirements. C4-Code is not used or reviewed as a C1/C2/C3 substitute.

### Findings

- **C1 focal contexts are not semantically complete.** The ACCSystem C1 overlay contains the focal system and a generic actors node, but omits several direct systems and relationships that the ACCSystem source and landscape record, including ACCommerce, ACManagement, both ACCMared applications, and the package CDN. Literal registry ID presence in the file does not demonstrate that these relationships appear in the view. The individual system views also duplicate a focal system node and draw a “system boundary” self-edge. A boundary is not another interacting system. These are confirmed diagram-content problems relative to the C4 scope definition. See `c1-context/c4-context-and-container-overlays.md` and the matching `c1-context/systems/SYS-*.md` sources. [1]
- **C2 view completeness and precedence are unclear.** Several overlay C2 views contain only internal container boxes and omit directly connected actors/systems documented in their C1 or container descriptions. ACCSystem has both a grouped overlay and a more detailed standalone C2 diagram; their external context and relations differ. No source says which one is authoritative or whether one is intentionally partial. The two drawings should be reconciled or explicitly scoped as complementary. [2]
- **C3 boundaries are generally recognizable but have precise defects.** Seven component diagrams cover the 28 registered components. The Integration diagram's heading names `CMP-INT-ORDERNOTIFY`, although its scope box decomposes `CNT-ACC-INTEGRATION`. The Payment diagram routes a provider webhook directly to `CMP-PAY-ORCHESTRATOR`, while `CMP-PAY-ADAPTER.md` identifies `CMP-PAY-ADAPTER` as first receiver and signature validator. The Identity diagram's authorization edge is underspecified. Several diagrams also show unregistered stores or helper nodes; these should be labeled as implementation detail or `PROPOSED`/`UNKNOWN`, not assumed to be registered components or approved technology. [3]
- **ID coverage is not semantic completeness.** The matrix's 7/7 C1, 30/30 C2, and 28/28 C3 literal-ID coverage is a useful inventory result. It does not prove that each view shows the relevant direct actors, external systems, boundaries, direction, or evidence-backed relationship.
- **Mermaid is a drawing format, not the C4 model.** A valid Mermaid parse or rendered image cannot establish C4 quality. Conversely, a tool error must not be treated as proof that a diagram is semantically wrong. The diagrams should be checked both structurally and against their source records.

## Microservices and distributed-system principles

The ACC documents use C2 names such as “service,” but do not establish that each container is an independently deployed microservice. Microsoft describes microservices as independently deployable, loosely coupled units that own their data and communicate through defined APIs, while also emphasizing distributed-system complexity, data consistency, operational load, and deployment trade-offs. [4] Its boundary guidance starts from domain responsibility/cohesion and non-functional needs, discourages chatty or jointly deployed boundaries, and allows related functionality to remain together where consistency requires it. It explicitly recommends pragmatic, coarse-grained starts when boundaries are uncertain. [5] These are design guidance, not mandatory ACC rules. A modular monolith or shared deployment of cohesive containers may be a valid deployment choice if it preserves the documented responsibility, data ownership, security, scaling, and release requirements. The package does not include runtime manifests or release evidence sufficient to decide that question.

### Findings and trade-offs

- **Documented domain boundaries are coherent at the stated level.** ACCore owns institution-side product, stock, and local ERP records; ACCSystem owns marketplace projections and central ParentOrder/SellerOrder lifecycle; Integration routes institution operations without owning stock or central order state. The search projection is described as derived/rebuildable. The reviewed sources do not establish that every logical container is a separate process, database, team, or deployable unit. No automatic service split is recommended.
- **Independent deployment remains unverified.** ACC scope requirements include deployment constraints (including NFR-011/CON-012 in the cited review), but the package lacks deployment topology, release-coupling, shared-state, team ownership, and CI/CD evidence. This is a verification gap, not proof of a design violation. The decision must consider actual boundaries, operational cost, and requirement interpretation.
- **Multi-seller reservation safety is well articulated but not implementation evidence.** The accepted multi-seller direction specifies a ParentOrder, seller-specific SellerOrders, and one reservation per seller at that seller's ACCore. The proposed saga rules preserve a dispatched timeout/lost response as `UNKNOWN`, query by stable reservation ID/idempotency key, block dependent payment, and avoid release/void/replay from elapsed time alone. These are strong written safeguards, not evidence of runtime behavior. Reservation TTL, reconciliation ownership/deadlines, retry values, and implementation tests remain gates. [6]
- **A source-level conflict undermines the safe saga rule.** `supporting-views/interface-contracts.md` includes a reservation timeout row that pairs “uncertain” and query with “compensate if no confirmation”; its TTL row says ACCore auto-releases and the saga compensates. These statements conflict with `CMP-INT-RESERVATION.md`, `CMP-CON-RESERVATION.md`, ADR-013, and ADR-006, which prohibit timeout-only rejection or release and require reconciliation or an approved safe-expiry rule. The generic `CNT-ACC-ORDERS.md` row “ACCore reservation fails” is ambiguous; by itself it is not sufficient evidence that a timeout is final. The interface/TTL conflict is confirmed and high impact because it could permit unsafe release. Do not silently resolve it by changing the decision record or inventing an expiry policy.
- **Data consistency follows distributed workflows, not one global transaction.** The saga reference describes coordinated local transactions and explicit compensation, and notes lack of automatic rollback/isolation. [6] The outbox reference explains how atomic local state plus event intent can avoid database/broker dual-write gaps, while duplicate delivery still requires idempotent consumers. [7] ACC describes outbox/inbox and idempotency, but a written pattern is not evidence of persistence, ordering, deduplication, or reconciliation correctness in deployed code.
- **Inter-institution trust and interface contracts remain approval gates.** The package documents institutional separation, connector-mediated access, authentication, and tenant boundaries. ADR-015 makes outbound-initiated connectivity the default for firewalled institutions while protected inbound connectivity is optional, whereas the ACCore C1 text and C3 diagram can be read as requiring inbound endpoints. This is a documentation inconsistency with security and deployment consequences. API/event schemas, response vocabulary, sync/callback behavior, key lifecycle, replay handling, and per-institution policy need a single versioned and approved contract. No specific connectivity mode is asserted here as owner-approved beyond the decision text itself.
- **Observability and operational readiness are not established.** The package marks several service targets and recovery values as unknown or proposed. Google SRE's latency, traffic, errors, and saturation signals are useful review guidance, not an ACC-mandated metric set or proof of readiness. [8] Recovery exercises, per-seller correlation, UNKNOWN/compensation aging, consumer lag, DLQ, and audit completeness need owner-approved targets and evidence.
- **Commercial, legal, provider, and institution policies remain external decisions.** Payment aggregation/capture, settlement, tax/accounting triggers, expiry, return/dispute policy, support consent, and institution onboarding must not be supplied by this audit. Retain `PROPOSED`/`UNKNOWN` labels and require the owners identified by the package.
