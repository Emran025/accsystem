# ADR-015 — Institution Connectivity and ACCore Release Trust

**Status:** PROPOSED ARCHITECTURAL BASELINE; explicit owner directions are labelled ACCEPTED-OWNER below.

## Decision
Use one logical ACCore connector contract, with its concrete version/schema mapping to be defined through ADR-021 and API Governance. The default deployment for firewalled institutions is outbound-initiated authenticated connectivity with polling/long-polling or a persistent channel. Protected inbound connectivity is optional. ACCore remains institution-owned and may be split or integrated as a package.

Authentication uses a policy-controlled adapter supporting OAuth 2.0 Client Credentials and mTLS. Neither method is enabled merely by client request; the security/operations policy selects the approved method set per institution. Credentials/certificates are rotated and revoked through onboarding and lifecycle workflows.

## Rationale and consequences
Outbound initiation avoids requiring inbound firewall exposure and supports reliable retry, but adds delivery latency and requires a durable local Outbox. Inbound mode may improve synchronous response time but requires network exposure and stronger perimeter controls. A reservation is successful only after a verified response; unknown outcomes remain recoverable UNKNOWN states.

Release trust requires signed artifact verification plus build provenance/attestation. Artifact hashes remain useful integrity checks but are not source-change detection. ACCore reports release and build fingerprints; mismatches notify the platform and are audited. Institution local changes remain institution responsibility.

## Evidence, status and open gates

The outbound-initiated default, optional protected inbound, integrated/split ACCore packaging, policy-selected OAuth/mTLS and release-provenance direction are proposed baselines, not universal approvals. Traceability links include `supporting-views/deployment-view.md`, `c2-containers/accore/CNT-ACR-CONNECTOR.md`, `validation/c4-microservices-remediation-plan.md` (RP-02/RP-16), and the stakeholder review gate. No named approval is asserted. Logical delivery direction must not be read as a mandatory transport-initiation mode.

Required digest/signature verification and applicable provenance checks prevent publication as Available when they fail; a deployed fingerprint mismatch produces an auditable notification, while the institution response remains policy-gated. The described contract and security tests are planned scenarios unless execution evidence is linked.

## Confidence / Reversibility / Revisit

| Field | Value |
|---|---|
| Confidence | Medium for the connectivity/trust principles; exact transport, authentication, response modality and measurement trust are not approved |
| Reversibility | Medium before institution onboarding and release-signing adoption; lower after contracts, credentials and artifacts are deployed |
| Affected elements | CNT-ACR-CONNECTOR, CNT-ACC-INTEGRATION, CNT-ACC-SOFTCAT, deployment and security views |
| Revisit trigger | Institution/API/security onboarding, contract approval, signing-pipeline implementation, trusted measurement evidence, or material connectivity/release policy change |

## Verification
Contract tests cover both connectivity modes, credential rotation/revocation, duplicate commands, channel interruption, unknown reservation outcomes, and release fingerprint mismatch. Production enablement requires security review and institution onboarding evidence.
