# ADR-022 — Configurable Policy Registry and No Hard-Coded Thresholds

**Decision ID:** ADR-022
**Status:** ACCEPTED (architecture principle); PROPOSED/approval-required (specific numeric values per institution)
**Date:** 2026-11-19
**Evidence:** ADR-013 §4, ADR-017; interface-contracts.md §3.4 (reservation_ttl_seconds); ADR-006 §3.2; open issues RP-01 (TTL field), RP-04 (accounting trigger); idea.md §12

---

## 1. Problem / Context

Multiple architecture documents contain thresholds, durations, and policy values that are either:
- **Left as `UNKNOWN`** (e.g., reservation hold TTL — ADR-006, idea.md §12)
- **Implied by field names** without numeric values (e.g., `reservation_ttl_seconds` in IF-ACC-RESERVE-SAGA)
- **Referenced in prose** without a declared owner or configuration mechanism (e.g., retry counts, reconciliation windows, capture timing, grace periods)

ADR-013 §4 explicitly states: *"Operational timeout values, retry policy, idempotency retention, and saga-record archival are configuration owned by Operations/SRE and approved using workload, recovery, legal, and audit evidence. No numeric target is asserted here."*

ADR-017 defines that ACCSystem stores versioned policy snapshots, but does not describe the mechanism by which these thresholds are stored, versioned, deployed, or validated.

This ADR fills that gap. It establishes:
1. The **principle** that all configurable thresholds are externalized (never hard-coded in architecture documents or application defaults)
2. The **policy registry** pattern for storing, versioning, and governing these values
3. A **registry of known configurable thresholds** with their owners and status

## 3. Decision

### 3.1 Core principle: no hard-coded numeric thresholds in architecture documents

**Architecture documents (ADRs, interface contracts, component specs) MUST NOT assert specific numeric values for:**
- Timeout durations (call timeouts, saga step timeouts, circuit breaker windows)
- TTL / hold durations (reservation TTL, idempotency key retention period)
- Retry counts and backoff intervals
- Reconciliation window durations
- Capture timing offsets
- Grace periods (payment capture after authorization, settlement deadlines)
- Validation intervals (license validation, policy refresh)
- Saga record archival retention periods

Instead, architecture documents MUST reference the threshold by name (e.g., `policy:reservation.hold_ttl_seconds`) and state the owner function responsible for approving the value.

### 3.2 Policy configuration store (companion to ADR-017)

The policy configuration store described in ADR-017 is the authoritative home for all configurable thresholds. Requirements:

| Requirement | Detail |
|---|---|
| **Versioned snapshots** | Each policy value change creates a new snapshot version; prior versions are immutable and auditable |
| **Institution-scoped** | Each institution (ACCore instance) may have different approved values; global defaults exist only as fail-closed fallbacks |
| **Owner-approved** | Each threshold has a declared owner function (Operations/SRE, Finance, Legal, Compliance, Product); a value change requires that owner's explicit approval record |
| **Referenced at confirmation** | A confirmed order stores the policy snapshot version in effect at confirmation time (per ADR-016, ADR-019) |
| **Fail-closed defaults** | In the absence of an institution-specific approved value, the system defaults to the most restrictive safe behavior (e.g., zero retries, no auto-release, manual escalation) — not to a guessed numeric value |
| **Change audit trail** | All changes to policy values are logged with actor, timestamp, approval reference, and justification |

### 3.3 Fail-closed default behavior

When a policy value is not yet approved for a given institution, the system MUST:

| Scenario | Fail-closed behavior |
|---|---|
| `reservation.hold_ttl_seconds` not configured | Treat reservation as indefinitely held; alert Operations; do not auto-release |
| Saga step call timeout not configured | Use the system-minimum safe timeout (longest reasonable wait); do not timeout aggressively |
| Reconciliation window not configured | Escalate to PENDING_REVIEW immediately on UNKNOWN; do not auto-resolve |
| Capture timing not configured | Do not auto-capture; flag for manual Finance review |
| Retry count not configured | Zero automatic retries; alert Operations |

> [!CAUTION]
> Fail-closed defaults are intentionally conservative and will cause operational alerts until institution policies are properly configured and approved. This is by design — a system that runs silently with no approved policy values is more dangerous than one that alerts loudly.

### 3.5 Architecture document annotation rule

When an architecture document references a configurable threshold, it MUST use this notation:

```
`policy:{threshold.name}` — configurable; owner: {OwnerFunction}; approved value required before production activation (ADR-022)
```

Example:
> The reservation hold TTL is `policy:reservation.hold_ttl_seconds` — configurable; owner: Operations/SRE + Finance; approved value required before production activation (ADR-022).

This replaces any numeric value or `UNKNOWN` placeholder in the document.

## 4. Change-later Mechanism

| Item | How to change |
|---|---|
| A specific threshold value | Owner-approved policy config store update; no ADR change required |
| Adding a new threshold to the registry | Update §3.4 of this ADR; owner declares the responsible function |
| Fail-closed default behavior for a specific threshold | Update §3.3 table; requires Operations/SRE approval |
| Policy store infrastructure design | Separate technical ADR if the implementation deviates from ADR-017 descriptions |

---

## 5. Assumptions

1. ACCSystem's policy configuration store (per ADR-017) can store and version all threshold types listed in §3.4.
2. Each institution completes a policy configuration approval step as part of onboarding; production activation is blocked until all required thresholds have approved values.
3. The policy store is the single source of truth; threshold values in code, environment variables, or configuration files are overridden by the policy store or are explicitly declared as local deployment config (not architecture config).
4. Owner functions listed in §3.4 are real organisational roles that can provide and approve values before production deployment.

## 6. Impact and Risks

| Impact / Risk | Severity | Mitigation |
|---|---|---|
| Institution onboarding stalls due to missing approved policy values | High | Onboarding checklist explicitly lists required threshold approvals; no production capability activation without them |
| Developer uses a hard-coded value in code "temporarily" | High | Code review checklist; architecture review gate; ADR-022 cited in engineering standards |
| Policy store unavailable at runtime | Medium | Services cache the last-approved snapshot; alert on stale cache; fail-closed for new operations |
| Threshold approved with wrong value causes operational failure | Medium | Owner-approval trail enables rapid rollback to prior snapshot version |
| Registry becomes stale (new thresholds not added) | Low | ADR review is a standing agenda item in architecture review meetings |

## 7. Acceptance Test

1. **No numeric values in architecture documents:** A grep of all ADR and interface-contract files for bare numeric timeout/TTL/retry values returns zero matches (excluding examples explicitly labelled as illustrative and cross-referencing this ADR). ✓
2. **Fail-closed on unconfigured threshold:** A test environment with no policy store configuration causes the reservation workflow to escalate to PENDING_REVIEW (not to auto-release or auto-compensate). ✓
3. **Policy snapshot immutability:** Modifying a threshold in the policy store creates a new snapshot version; querying a confirmed order's policy snapshot version returns the original values, not the updated ones. ✓
4. **Owner approval required:** Attempting to activate a production capability (e.g., auto-capture) without an approved `payment.capture_timing_hours` value is blocked by the onboarding workflow. ✓
5. **Registry completeness check:** All thresholds in §3.4 have a named owner function; no threshold has a numeric value in the ADR itself. ✓
6. **Threshold annotation in documents:** References to configurable thresholds in interface-contracts.md and component specs follow the `policy:{threshold.name}` annotation pattern from §3.5. ✓
