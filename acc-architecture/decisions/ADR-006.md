# ADR-006 — Inventory Reservation at ACCore Before Order Confirmation

**Decision ID:** ADR-006  
**Status:** PROPOSED  
**Date:** 2026-11-15  
**Evidence:** idea.md §4.3, §8, §12

---

## 1. Problem / Context

Multi-seller orders require that each seller's inventory is committed before payment is authorized and the order is confirmed. The question is when and where inventory reservation occurs and what happens if it fails.

---

## 2. Alternatives Considered

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — Synchronous reservation at ACCore before payment** (selected) | Saga Step 1: reserve all sellers' inventory (synchronous calls to each ACCore) before proceeding to payment | + Prevents overselling. + Clear compensation path. — Latency: N serial or parallel calls to N ACCore instances. — ACCore must be online during checkout. |
| **B — Optimistic reservation (reserve at confirmation only)** | Confirm order first, then reserve; fail order if reservation fails post-payment | + Faster checkout. — Overselling risk. — Complex compensation (void payment after charge). |
| **C — ACCSystem owns inventory replica** | ACCSystem holds a real-time stock replica | + Fast reservation. — Data ownership conflict (ADR-001). — Complex synchronization. |

---

## 3. Decision

**Inventory reservation occurs at ACCore as Saga Step 1 (before payment authorization).** Each seller's ACCore receives the logical `ReservationRequest`; synchronous response is the default transport, while an approved institution may use the ADR-015/018 callback mode. All sellers must reserve successfully before the saga proceeds to payment. On authoritative failure or expiry, relevant peer outcomes are reconciled; only eligible confirmed holds are released under the UNKNOWN guard, and the saga closes only after required compensation is settled.

Reservation hold TTL (auto-release if saga stalls) is **UNKNOWN** and represented as `policy:reservation.hold_ttl_seconds` under ADR-022; no value or owner approval is asserted (idea.md §12 — open decision).

### 3.1 Payment outcome and timeout semantics

| Topic | Current documents state | Proposed architectural decision |
|---|---|---|
| Authorization timeout | Some flows treat timeout as a normal failure path and trigger compensation immediately. | A timeout is not proof that authorization failed. The payment record enters `AUTHORIZATION_UNKNOWN` / `PaymentUnknown` and is retried or reconciled. |
| Reservation release | Immediate release may follow payment timeout. | Reservation is not released merely because the provider did not answer in time. The hold remains until the provider outcome is known or a compensating final failure is confirmed. |
| Order confirmation boundary | A definitive approved payment outcome is required before confirmation. | A payment result must be known as an approved mode-specific outcome: `AUTHORIZED` for authorize-then-capture or `CAPTURED` for approved immediate capture; `DECLINED`/failure blocks confirmation, and `UNKNOWN` blocks final confirmation and any action with financial effect. |

This ADR therefore defines the rule: a timeout or missing provider response is an uncertainty state, not a final failure state. Before any action that could repeat a financial effect or release a reservation, the system must resolve the current payment state via retry, webhook, or reconciliation. If the provider later confirms no authorization was created, the system may then treat the authorization as failed and compensate. If the provider confirms an authorization exists, the system continues from that final state. In other words, unknown is a recovery state, not evidence of decline.

### 3.2 Safe reservation-hold rule when payment remains unknown

This is the time-boundary rule that prevents premature inventory release while payment may still exist:

- If `Payment.state = AUTHORIZATION_UNKNOWN` and the reservation is not yet expired, the reservation must remain `HELD` and must not be released by timeout logic alone.
- If the reservation is in a safety window near expiry, the system must escalate to `PendingPaymentReview` and trigger an immediate follow-up reconciliation with the payment provider before any release or retry that could create a second financial effect.
- A reservation may be released after relevant peer reconciliation when there is definitive evidence of a known non-payment/failure before dispatch, a definitive final payment outcome (`DECLINED`, `FAILED`, or `VOIDED`), or an explicit manual cancellation approved by the operations owner for a known non-payment scenario. Unknown dispatch or elapsed time alone never authorizes release.
- A payment timeout does not authorize the system to treat the reservation as expired if the provider may still have an authorization in flight.

This is a temporary safe assumption until the exact reservation hold TTL, payment reconciliation deadline, and escalation ownership are approved by the responsible operational authority. The missing values are not yet finalized and must be fixed by the deployment/operations owner before production use.

## 4. Rationale

- CONFIRMED (idea.md §4.3): Reservation is an ACCore responsibility.
- Prevents overselling without ACCSystem owning inventory.
- Saga compensation (ADR-013) handles partial failures.

## 5. Consequences, Risks, Mitigations

| Consequence | Type | Mitigation |
|---|---|---|
| ACCore must be online during checkout | Availability constraint | Circuit breaker limits new attempts; before dispatch a local unavailable result may be shown, while after dispatch the reservation remains UNKNOWN and is reconciled |
| Checkout latency increases with N sellers | Performance | Parallel reservation calls for multi-seller orders (PROPOSAL) |
| Orphan holds if saga stalls | Operational risk | Auto-release TTL (UNKNOWN); manual monitoring of RESERVED → long-held |
| Reservation TTL undefined | UNKNOWN — `policy:reservation.hold_ttl_seconds` | Owner: OWNER_UNASSIGNED; revisit trigger: operational SLAs and owner approval |
