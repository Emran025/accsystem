# ADR-012 — ACCSystem Service Architecture: Bounded-Context Logical Services with Coarse-Grained Deployment Units

**Decision ID:** ADR-012  
**Status:** PROPOSED  
**Date:** 2026-11-15 (revised for consistency alignment)  
**Evidence:** idea.md §3.1, §14; scope-and-requirements.md §7

---

## 1. Problem / Context

ACCSystem must provide 17 distinct functional capabilities (Catalog, Orders, Payment, Identity, License, etc.). Three aspects must be distinguished clearly to avoid architectural confusion:

1. **Logical bounded contexts** — the domain separation that governs data ownership, API contracts, and team ownership
2. **Deployment units** — the actual runtime processes/containers that are packaged and deployed together
3. **Scaling units** — the granularity at which capacity is independently added

These three levels need not be identical. Conflating them creates the apparent contradiction between "17 services" and "5–6 services" found in earlier documents.

---

## 2. Alternatives Considered

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — Monolith** | All ACCSystem domains in one deployable unit | + Simplest ops. — Cannot scale or deploy domains independently. — Contradicts idea.md §3.1 domain separation. |
| **B — Full microservices (17 independent deployments)** | Each of the 17 bounded contexts is independently deployed from day 1 | + Maximum isolation. — Very high operational overhead. — Team maturity and infrastructure requirements are UNKNOWN. |
| **C — Coarse-grained services with bounded-context internals** (selected) | 5–6 independently deployable runtime units; each unit internally enforces domain boundaries (no cross-domain DB access); high-load domains extracted on evidence | + Bounded-context data isolation maintained. + Manageable operational overhead. + Clear migration path to finer granularity. — Inter-domain calls within a service unit are still in-process (acceptable). |

---

## 3. Decision

**ACCSystem is designed as 17 logical bounded contexts, deployed as 5–6 coarse-grained service units, with selective extraction of high-load domains.**

### Three-layer model (authoritative)

| Layer | Description | Count |
|---|---|---|
| **Logical Bounded Contexts** | Domain boundaries — each context owns its own data schema, API contract, and team ownership. Never share databases across context boundaries, even within the same deployment unit. | **17** (all containers in C2) |
| **Initial Deployment Units** | Runtime process groups packaged and deployed together at launch. Each unit may host multiple bounded contexts in separate in-process modules or as a local cluster. | **5–6** (see below) |
| **Extraction Candidates** | Individual bounded contexts that may be extracted into standalone deployments as scaling evidence demands, without redesign, because domain boundaries were enforced from day 1. | Per evidence trigger |

### Initial Deployment Unit Grouping (PROPOSED)

| Deployment Unit | Bounded Contexts Included | Extraction Trigger |
|---|---|---|
| **Commerce Service** | CNT-ACC-CATALOG, CNT-ACC-SEARCH, CNT-ACC-OFFER, CNT-ACC-CART, CNT-ACC-ORDERS | Extract CNT-ACC-SEARCH if search p99 > 2s under load |
| **Fulfilment Service** | CNT-ACC-PAYMENT, CNT-ACC-DELIVERY, CNT-ACC-NOTIFICATIONS | Extract CNT-ACC-PAYMENT if payment latency or PCI scope isolation requires it |
| **Institution Integration Service** | CNT-ACC-INTEGRATION, CNT-ACC-EVENTBUS | Extract if event throughput exceeds Commerce Service capacity |
| **Platform Management Service** | CNT-ACC-SOFTCAT, CNT-ACC-LICENSE, CNT-ACC-PLATFORMADMIN | Extract CNT-ACC-LICENSE if offline token generation becomes a bottleneck |
| **Platform Access Service** | CNT-ACC-APIGATEWAY, CNT-ACC-IDENTITY, CNT-ACC-INSTREG | Identity is a hot path — monitor and extract first if latency degrades |
| **Observability Service** | CNT-ACC-AUDIT | Shared infrastructure; dedicated deployment from day 1 for append-only isolation |

> [!IMPORTANT]
> **Enforcement rule:** Even within a shared deployment unit, bounded contexts must **never share database schemas**. Each context owns its own schema (or separate DB instance). Cross-context data access is always via API or event — never via direct DB query. This is the invariant that makes later extraction possible without redesign.

> [!NOTE]
> The scope-and-requirements.md §7.3 and deployment-view.md §3.3 describe the same 5–6 service grouping. Those documents are aligned with this ADR. The number "17" refers to logical bounded contexts; "5–6" refers to initial deployment units. Both are correct at their respective levels of description.

- CONFIRMED (idea.md §3.1): 17 distinct domain modules listed — this establishes the logical bounded-context count
- CONFIRMED (scope-and-requirements.md §7): Analysis recommends coarse-grained services as initial architecture style given UNKNOWN team topology and operational maturity
