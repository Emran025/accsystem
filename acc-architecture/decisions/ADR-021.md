# ADR-021 — Interface Versioning Interim Policy

**Decision ID:** ADR-021
**Status:** PROPOSED/approval-required (pending formal API governance approval)
**Date:** 2026-11-19
**Evidence:** interface-contracts.md §10 (IC-002); ADR-015; open issue IC-001

---

## 1. Problem / Context

The ACC V5 architecture defines multiple named interfaces (`IF-ACC-RESERVE-SAGA`, `IF-ACR-RESERVATION-RESP`, `IF-ACC-ORDER-CONFIRM`, etc.) but no versioning policy governs them. Without a declared policy:

- Implementers do not know when a change requires a new version vs. is backward-compatible
- Consumers cannot predict when they must update their integrations
- Multiple teams may apply conflicting versioning strategies to different interfaces
- Breaking changes may be deployed without adequate notice, breaking running institutions

This ADR establishes an **interim** conservative versioning policy pending formal API governance process approval.

## 2. Alternatives Considered

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — URI-path major versioning (candidate / PROPOSED)** | Applicable interfaces could use a URI path prefix such as `/v1/`. Within an approved major version, only additive backward-compatible changes would be allowed. Breaking changes would require a new major version with an approved deprecation overlap. | + Simple to implement. + Clear consumer signal when breaking change occurs. + Common industry pattern. — Major version proliferation if changes are frequent. — An overlap period costs maintenance. |
| **B — Header-based versioning (Accept: application/vnd.acc.v1+json)** | Version negotiated via Accept header | + Clean URLs. — Less visible in logs and gateway routing. — More complex client implementation. |
| **C — No versioning / always latest** | Single endpoint, no version | — Breaking changes are silent. — Consumer integrations break without notice. — Unacceptable for multi-institution architecture. |
| **D — Semantic versioning with minor versions exposed** | /v1.1/, /v1.2/ etc. | — Complex routing. — Minor versions rarely justified for public APIs. — Overkill for current scale. |

## 3. Decision

### 3.1 Versioning scheme (PROPOSED/approval-required)

Applicable ACCSystem-controlled HTTP interfaces may use **URI-path major versioning as a proposal**. Broker events, provider-owned webhooks, connector delivery and other non-HTTP or externally controlled contracts require their own approved schema/version treatment; no universal transport version is asserted:

| Rule | Detail |
|---|---|
| URI pattern | `/{system-prefix}/v{MAJOR}/{resource-path}` e.g. `/acc/v1/reservations` |
| Initial version | A candidate initial major (illustrated as `/v1/`) for applicable platform-controlled HTTP interfaces; actual path and initial version require contract/API Governance approval |
| Additive changes within a major | Candidate only when approved schemas, tolerant consumers, semantic compatibility and contract evidence show safety; otherwise migrate/version |
| Breaking changes (require new major version) | Removing fields, renaming fields, changing field types, changing required/optional status of existing fields, changing status vocabulary, removing endpoints |
| Deprecation notice | Proposed six-calendar-month overlap and migration notice, subject to API Governance, consumer inventory, provider and institutional/legal review |
| Version sunset | A version is retired only after the deprecation window elapses AND all known consuming institutions have confirmed migration |

> [!IMPORTANT]
> **PROPOSED/approval-required:** This policy is an interim recommendation, not a binding cross-institution rule. Teams must not treat the URI pattern, any initial major-version assignment, a deprecation interval or amendment constraints as approved contractual commitments before API Governance and affected owners review them.

### 3.2 Additive-only rule within a major version

The following are **candidate additive changes** (permitted without a new major version only after the applicable contract, consumer and governance review):
- New **optional** fields in request or response bodies
- New enum values only in fields explicitly marked `[extensible]` in an approved contract, with a safe documented unknown-value behavior
- New endpoints within the same major version prefix
- New response error codes (consumers must handle unknown error codes gracefully)
- New optional query parameters

The following are **breaking changes** (require a new major version and deprecation notice):
- Removing or renaming any field
- Making an optional field required
- Changing a field's data type or format
- Changing the semantic meaning of an existing field or status code
- Removing or renaming an endpoint
- Changing an authentication or authorization requirement

### 3.3 Interface-contracts.md reference IDs

Existing `IF-*` interface identifiers in interface-contracts.md do **not** carry an implicit major version while this ADR is pending. After governance approval, each applicable interface must receive an explicit version/path mapping in its contract. If a major version changes, the approved mapping and retained deprecated contract must be recorded; an ID suffix such as `-V2` is only illustrative until that mapping is approved.

### 3.4 Closed enums vs. open enums

Status vocabulary fields that are declared as **canonical closed enums** (e.g., `ACCEPTED` / `REJECTED` / `UNKNOWN` / `EXPIRED` per ADR-018) are not extensible without a major version bump. Consumers may assert that any undocumented value is an error.

Fields declared as **open/extensible enums** (marked `[extensible]` in interface-contracts.md) allow new values to be added within a major version; consumers MUST treat unknown values as an equivalent of the documented catch-all.

## 5. Assumptions

1. API consumers (ACCore connector, ACCommerce app, institution integrations) can be identified and notified for deprecation windows.
2. URI-path versioning is supported by the API gateway (CNT-ACC-APIGATEWAY) routing configuration.
3. No current interface has an approved major-version mapping; no interface is treated as beginning at v1 under this pending policy.
4. The 6-month deprecation window is achievable given the institution onboarding and release cadence; if not, this policy requires a governance review.

## 6. Impact and Risks

| Impact / Risk | Severity | Mitigation |
|---|---|---|
| Team applies different versioning strategy before governance approval | Medium | This ADR is a candidate policy only; implementation contracts must remain explicitly unassigned until governance approval |
| 6-month window is too short for some institutions | Medium | Governance review can extend; conservative default errs on longer |
| "Additive" change that is functionally breaking | Medium | Peer review checklist; contract tests for all consumer personas |
| Version proliferation (many v2, v3 interfaces) | Low | Additive-only within major version reduces version bump frequency |
