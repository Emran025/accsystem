# ADR-020 — C2 View Scope Declaration and C1 Arrow Convention

**Decision ID:** ADR-020
**Status:** ACCEPTED (documentation convention; no institutional authority required)
**Date:** 2026-11-19
**Evidence:** c2-containers/*/container-diagram.md files; c1-context/c4-context-and-container-overlays.md; open issues RP-07, RP-08, RP-09, RP-10

---

## 1. Problem / Context

Two related documentation ambiguities were identified in the architecture diagrams:

**RP-09 / RP-10 — C2 view scope not declared:**
The C2 container diagrams for each system (ACCSystem, ACCore, ACCommerce, ACManagement, ACCMared) show internal containers and selected relationships. However, no diagram carries a scope declaration. Readers may assume the views are complete representations of all external collaborators, leading to:
- False confidence that undepicted relationships do not exist
- Integration work based on incomplete context
- Review gate confusion when a diagram "looks complete" but isn't

**RP-07 / RP-08 — C1 arrow convention not defined:**
The C1 context diagram (`c1-context/c4-context-and-container-overlays.md`) contains arrows between systems and containers, but the direction convention is not stated. Arrows could mean:
- Data flow direction (data moves in arrow direction)
- Control/initiation direction (initiating party points toward target)
- Dependency direction (dependent points toward depended-upon)

Without a declared convention, reviewers interpret arrows differently, leading to disagreement about which system "calls" which.

## 2. Alternatives Considered

### C2 scope declaration

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — Add scope header to each C2 file (selected)** | Standardized header note in each C2 diagram file: "Internal view — does not claim context-completeness. External collaborators documented in container records but not all shown here." | + Zero rework of diagram content. + Immediate reader clarity. + Reversible (remove header if view becomes complete). |
| **B — Enumerate all external collaborators in each diagram** | Make all C2 views context-complete | — Large effort. — Diagrams become unreadable with many external actors. — Not the purpose of C2 decomposition view. |
| **C — Add "incomplete" watermark** | Mark diagrams as work-in-progress | — Implies temporarily incomplete rather than intentionally scoped. |

### C1 arrow convention

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — Control/data-flow initiator direction (selected)** | Arrow points from the initiating component toward the target. "A → B" means A initiates the call/message to B. | + Matches most developer mental models. + Consistent with C4 Model convention. + Easy to verify: who sends the first message? |
| **B — Data flow direction** | Arrow shows where data moves | — Ambiguous in request/response (data flows both ways). — Conflicts with C4 Model convention. |
| **C — Dependency direction** | Arrow shows what a component depends on | — Different from C4 convention. — Confusing when combined with collaboration arrows. |

---

## 3. Decision

### 3.1 C2 view scope declaration

**All C2 container diagram files** MUST carry the following header note (in addition to any existing headers), placed immediately after the document title / first heading:

```markdown
> [!NOTE]
> **Scope declaration — Internal view:** This diagram shows the internal container decomposition of [System Name]. It does not claim context-completeness. External collaborators and integration points are documented in the individual container records (CNT-* files) and in the C1 context diagram, but not all external actors are shown in this view.
```

The `[System Name]` placeholder is replaced with the specific system name in each file.

This declaration applies to all C2 files currently in `c2-containers/*/container-diagram.md`.

### 3.2 C1 arrow convention

**Arrow direction in all C1 and C4 overlay diagrams represents the control/data-flow initiator:**

> Arrow A → B means: **A initiates the interaction** (sends a request, publishes an event, or opens a connection) **to B**.

This follows the C4 Model convention. It does NOT imply that data only flows in the arrow direction (responses, callbacks, and events may flow in the reverse direction).

**A legend note MUST be added** to `c1-context/c4-context-and-container-overlays.md`:

```markdown
> [!NOTE]
> **Arrow convention:** Arrows show the **control/data-flow initiator direction**. An arrow from A to B means A initiates the call, message, or connection to B. Response data, callbacks, and events may flow in either direction and are not separately depicted unless explicitly labelled. This convention follows the C4 Model.
```

### 3.3 Scope of this decision

This ADR governs **documentation conventions only**. It does not alter any container responsibilities, interface contracts, or deployment topology. Diagrams remain correct; only their declared scope and arrow semantics are made explicit.

|---|---|
| Scope header wording | Edit the header in affected files; update this ADR's §3.1 template |
| Arrow convention | Requires a new ADR superseding §3.2; all diagrams must be audited for consistency after any convention change |
| Transition to context-complete C2 views | Remove scope declaration header from individual files when completeness is verified; update this ADR's scope list |

---

## 5. Assumptions

1. C2 views are intentionally scoped to internal decomposition; they are not intended to replace the C1 context diagram for external relationship completeness.
2. The C4 Model initiator-direction convention is known to all architecture document contributors.
3. Container records (CNT-* files) are the authoritative source for each container's external collaborators.
