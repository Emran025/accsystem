# ADR-020 — C2 View Scope Declaration and C1 Arrow Convention

**Decision ID:** ADR-020
**Status:** TECHNICAL BASELINE RECORDED; OWNER-REVIEW-REQUIRED and NOT STAKEHOLDER-APPROVED. The convention is reversible and does not by itself establish institutional authority.
**Date:** 2026-11-19
**Evidence:** `c2-containers/accsystem/container-diagram.md` (canonical ACCSystem C2 view); `c1-context/context-diagram.md` (canonical ACCSystem C1 view); `c1-context/c4-context-and-container-overlays.md`; open issues RP-07, RP-08, RP-09, RP-10

---

## 1. Problem / Context

Two related documentation ambiguities were identified in the architecture diagrams:

**RP-09 / RP-10 — C2 view scope not declared:**
The canonical C2 container view for ACCSystem and the registry-derived C2 overlays for the other systems show internal containers and selected relationships. The canonical C2 view now carries an explicit scope declaration. Readers may assume the views are complete representations of all external collaborators, leading to:
- False confidence that undepicted relationships do not exist
- Integration work based on incomplete context
- Review gate confusion when a diagram "looks complete" but isn't

**RP-07 / RP-08 — C1 arrow convention not defined:**
At the time this ADR was recorded, the ACCSystem C1 context and overlay diagrams did not state an arrow-direction convention. The canonical ACCSystem C1 view is now `c1-context/context-diagram.md`; the separate overlay collection is `c1-context/c4-context-and-container-overlays.md`. Arrows could mean:
- Data flow direction (data moves in arrow direction)
- Control/initiation direction (initiating party points toward target)
- Dependency direction (dependent points toward depended-upon)

Without a declared convention, reviewers interpret arrows differently, leading to disagreement about which system "calls" which.

## 2. Alternatives Considered

### C2 scope declaration

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — Add scope header to the canonical C2 view (selected)** | Standardized header note in each C2 diagram file: "Internal view — does not claim context-completeness. External collaborators documented in container records but not all shown here." | + Zero rework of diagram content. + Immediate reader clarity. + Reversible (remove header if view becomes complete). |
| **B — Enumerate all external collaborators in each diagram** | Make all C2 views context-complete | — Large effort. — Diagrams become unreadable with many external actors. — Not the purpose of C2 decomposition view. |
| **C — Add "incomplete" watermark** | Mark diagrams as work-in-progress | — Implies temporarily incomplete rather than intentionally scoped. |

### C1 arrow convention

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — Logical interaction source-to-target (selected project convention)** | Arrow A → B means A is the logical requester or sender in the depicted interaction; it does not identify physical network-connection initiation. | + Distinguishes message/request direction from transport policy. + Can be checked against a documented relationship. |
| **B — Data-flow direction** | Arrow shows where information moves; requests, responses, callbacks and events may flow in different directions. | — A single relationship can become ambiguous or require multiple arrows when responses are included. |
| **C — Dependency direction** | Arrow points from a dependent to the capability it depends on, which may differ from the message sender/recipient. | — In an interaction view, readers may confuse dependency with communication direction. |

---

## 3. Decision

### 3.1 C2 view scope declaration

**The canonical C2 container view** MUST carry the following header note (in addition to any existing headers), placed immediately after the document title / first heading:

```markdown
> [!NOTE]
> **Scope declaration — Internal view:** This diagram shows the internal container decomposition of [System Name]. It does not claim context-completeness. External collaborators and integration points are documented in the individual container records (CNT-* files) and in the C1 context diagram, but not all external actors are shown in this view.
```

The `[System Name]` placeholder is replaced with the specific system name in each file.

This declaration applies to the canonical ACCSystem C2 view at `c2-containers/accsystem/container-diagram.md`; registry-derived overlays retain their own scope labels and do not replace the canonical graph.

### 3.2 C1 arrow convention

**Arrow direction in all C1 and C4 overlay diagrams represents the logical interaction initiator:**

> Arrow A → B means: **A initiates the logical interaction** (sends a request or publishes a message/event to B).

This is the selected ACCSystem documentation convention for these C1/C4-overlay diagrams, not a claim about a universal C4 arrow rule. It does NOT imply that data only flows in the arrow direction (responses, callbacks, and events may flow in the reverse direction), and it does NOT specify which party initiates the physical network connection. Transport initiation is deployment policy governed by ADR-015 and institution onboarding; it must not be inferred from a C1/C4 arrow. For documented bidirectional capabilities, show separately labelled logical flows only when source evidence supports them.

**A legend note MUST be present** in the canonical `c1-context/context-diagram.md` and in `c1-context/c4-context-and-container-overlays.md` wherever the overlay uses arrows:

```markdown
> [!NOTE]
> **Arrow convention:** Arrows show the **logical interaction initiator**. An arrow from A to B means A initiates the request or message to B; it does not specify physical network-connection initiation. Response data, callbacks, and events may flow in either direction and are not separately depicted unless explicitly labelled. Transport mode is governed separately by ADR-015 and the institution's approved deployment policy.
```

### 3.3 Scope of this decision

This ADR governs **documentation conventions only**. It does not alter any container responsibilities, interface contracts, or deployment topology. Diagrams remain correct; only their declared scope and arrow semantics are made explicit.

|---|---|
| Scope header wording | Edit the header in affected files; update this ADR's §3.1 template |
| Arrow convention | Requires a new ADR superseding §3.2; all diagrams must be audited for consistency after any convention change |
| Transition to context-complete C2 views | Remove the scope declaration from the canonical view when completeness is verified; update this ADR's scope list |

---

## 5. Assumptions

1. The canonical C2 view is intentionally scoped to internal decomposition; they are not intended to replace the C1 context diagram for external relationship completeness.
2. Contributors can apply the project-level arrow convention only where source material identifies a logical requester/sender; ambiguous relationships require source or owner review rather than inference.
3. Container records (CNT-* files) are the authoritative source for each container's external collaborators.
