# ADR-013 — Saga Orchestration Pattern for Distributed Order Transaction

**Decision ID:** ADR-013  
**Status:** PROPOSED  
**Date:** 2026-11-15  
**Evidence:** idea.md §8, §14

## 1. Problem / Context

Checkout spans ACCSystem order/payment components, integration relays, each seller's ACCore, and external payment providers. No distributed ACID transaction spans these boundaries. A saga is therefore a persisted coordination workflow, not an atomic transaction and not a promise that every failure can be rolled back automatically.

The orchestrator must distinguish a local failure before dispatch, a definitive external rejection/failure, and an unknown outcome after a command may have been received. Each SellerOrder, Reservation, PaymentAttempt, capture, and compensation has independent state and idempotency evidence.

## 2. Alternatives Considered

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — Saga Orchestration** (selected proposal) | CMP-ORD-SAGA explicitly controls steps, state, queries, and conditional compensation | Central state and testability; requires durable recovery and reconciliation |
| **B — Saga Choreography** | Services react to events independently | More decoupled; harder to reason about aggregate state and compensation |
| **C — 2-Phase Commit** | Distributed transaction across services/providers | Not feasible across ACCore and external payment systems |

## 3. Decision

CMP-ORD-SAGA is the proposed parent coordinator. It persists one parent workflow and seller-scoped sub-operations:

| Step | Forward action | Conditional recovery/compensation |
|---|---|---|
| Reservation per SellerOrder | Send idempotent ReservationRequest to the relevant ACCore | If ACCore definitively rejects, compensate only other reservations confirmed accepted. If timeout/disconnect follows dispatch, persist `UNKNOWN`, query by reservation ID/key, and do not release until state is resolved or an approved ACCore safe-expiry rule applies. |
| PaymentAttempt per SellerOrder or compatible aggregate | Authorize/capture according to seller/agreement policy | Definitive decline permits compensation of confirmed reservations. Unknown authorization/capture requires provider query/reconciliation; no duplicate financial effect or blind void. |
| Parent/Seller confirmation | Commit snapshot, state transition, and outbox in one local transaction | Local failure before commit permits local rollback/retry. If an external effect may already exist, query/reconcile before retry or compensation. |
| Post-confirmation operations | Inventory commit, capture, seller credit, settlement, delivery, license lifecycle | Independent idempotent state machines; failures remain explicit pending/failed/unknown exceptions and are reconciled, not implicitly rolled back as a saga. |

Compensation is specific to the affected SellerOrder/Reservation/PaymentAttempt. Every compensation command has its own idempotency key and outcome state. A compensation failure or unknown result becomes `COMPENSATION_PENDING` or `COMPENSATION_UNKNOWN`, remains open for idempotent retry/reconciliation, and is escalated; the saga is not closed as definitively failed until the state is known.

## 4. State and timeout rules

- Local non-dispatch failure: the command was not sent according to durable dispatch evidence; local transaction may roll back or retry.
- Definitive rejection/failure: authoritative ACCore/provider evidence permits the documented conditional compensation.
- Timeout, circuit-open, connection loss, or lost response after a command may have been sent: persist `UNKNOWN`, stop dependent steps, query/reconcile using reference and idempotency key, and do not release, void, or repeat a side effect solely because time elapsed.
- Operational timeout values, retry policy, idempotency retention, and saga-record archival are configuration owned by Operations/SRE and approved using workload, recovery, legal, and audit evidence. No numeric target is asserted here; archival must not discard reconciliation or audit state.

## 5. Consequences, Risks, and Mitigations

| Consequence | Type | Mitigation |
|---|---|---|
| Compensation may fail or remain unknown | Critical risk | Persist compensation state, retry idempotently under Operations/SRE policy, alert, and require reconciliation/manual intervention. |
| Saga state grows with order volume | Operational | Use a configurable retention/archive policy approved by Operations/SRE, Legal, and Audit; retain all state needed for reconciliation and audit. |
| Partial completion visible during checkout | UX | Show Processing/Review states; do not show confirmed until the local confirmation transaction commits. |
| Circuit breaker prevents a new attempt | Operational | Treat open state as transport/availability information, not business rejection; preserve message and query/reconcile any prior dispatch. |
