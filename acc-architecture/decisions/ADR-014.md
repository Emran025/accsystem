# ADR-014 — Offline License Validation via Short-Lived Signed Entitlement Token

**Decision ID:** ADR-014  
**Status:** PROPOSED  
**Date:** 2026-11-15  
**Evidence:** idea.md §7, §12, §14

---

## 1. Problem / Context

ACCore instances may operate in environments with limited or no network connectivity (air-gapped institutions, offline operation). Licensed software running on ACCore must be validated without an online call to ACCSystem. The question is how to validate license entitlement offline without compromising security.

---

## 2. Alternatives Considered

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — Signed entitlement token** (selected) | ACCSystem issues short-lived tokens signed with its private key. ACCore validates using platform public key. | + No network call required. + Unforgeable (signature). + Time-bounded (expires). — TTL creates tradeoff: short = connectivity requirement, long = slow revocation. |
| **B — Always-online validation** | ACCore must call ACCSystem for every license check | + Instant revocation. — Breaks offline operation requirement. — Availability coupling. |
| **C — License key (static)** | Static license key bundled at installation | + Fully offline. — Cannot be revoked without reinstallation. — No time bounding. — Key sharing risk. |
| **D — HMAC-based challenge-response** | ACCSystem issues HMAC challenges offline | + Revocable with key rotation. — Key management complex. — HMAC key at ACCore = compromise risk. |

---

## 3. Decision

**ACCSystem generates short-lived signed entitlement tokens using asymmetric cryptography (private key at ACCSystem; public key distributed to ACCore).**

Illustrative **proposed**, workflow-discriminated claim sets (not a finalized wire format):

```json
{"workflow":"institutional","license_id":"lic_example","institution_id":"inst_example","product_code":"ACCORE","valid_from":"2026-01-01T00:00:00Z","valid_until":"2026-02-01T00:00:00Z","issued_at":"2026-01-01T00:00:00Z","expires_at":"2026-01-02T00:00:00Z","signature":"illustrative"}
```

```json
{"workflow":"marketplace","license_id":"lic_example","buyer_id":"buyer_example","product_id":"product_example","valid_from":"2026-01-01T00:00:00Z","valid_until":"2026-02-01T00:00:00Z","issued_at":"2026-01-01T00:00:00Z","expires_at":"2026-01-02T00:00:00Z","signature":"illustrative"}
```

These timestamps are examples, not a TTL decision. Institutional modules/seats and other approved claims remain supported. Grant validity (`valid_from`/`valid_until`) and credential issue/expiry are separate. Offline validation requires signed grant bounds or equivalent locally verifiable evidence in either workflow; absent required evidence must not grant access. Exact bound semantics including null/perpetual grants, wire names and any JWT `nbf`/`exp` mapping require Security/API/Product approval.

Validation at ACCore (CMP-CON-LICENSECHECK):
1. Verify signature using platform public key (private key never leaves ACCSystem)
2. Check credential expiry and applicable grant effective/validity bounds under the approved policy.
3. Select the claim set by workflow: institutional validation verifies `institution_id + product_code`; marketplace validation verifies `buyer_id + product_id`. The publisher institution remains seller identity and is not automatically the licensee.

**Token TTL:** UNKNOWN — represented as `policy:license.token_ttl` under ADR-022; this is a critical open decision (idea.md §12). Short or long values have different connectivity and revocation consequences; no value is selected.

**Grace period after expiry:** UNKNOWN — represented as `policy:license.expiry_grace_period` under ADR-022; OWNER_UNASSIGNED.

---

## 4. Rationale

- CONFIRMED (idea.md §14): Offline license validation via signed token is explicitly mentioned.
- CONFIRMED (idea.md §7): License management is an ACCSystem responsibility.
- Asymmetric cryptography: private key never at ACCore → compromise of ACCore cannot forge tokens.
- Time-bounding enables eventual revocation even in offline scenarios.
