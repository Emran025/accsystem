# ADR-019 — Financial Trigger Scope and Institutional Accounting Commitment Point

**Decision ID:** ADR-019
**Status:** PROPOSED/approval-required (institutional authority required for financial commitment policy)
**Date:** 2026-11-19
**Evidence:** idea.md §7.2, §8; ADR-016; interface-contracts.md §2A (IF-ACC-ORDER-CONFIRM); open issue RP-04

---

## 1. Problem / Context

The `OrderConfirmed` event is published by ACCSystem when the checkout saga reaches a successful final state (all required reservations accepted, definitive payment success for the approved authorization or supported immediate-capture path, and order persisted). The architectural ambiguity (RP-04) is:

**Does `OrderConfirmed` universally trigger a financial journal posting (ledger entry) in ACCore?**

If yes, the event envelope is implicitly a financial commitment instruction — a decision that requires institutional and legal/finance authority, not architectural authority alone. If no, the event is an informational state transition and each ACCore instance decides its own local commitment point.

The ambiguity creates risk: if some implementations treat `OrderConfirmed` as the universal ledger commitment trigger and others do not, revenue recognition, audit trails, and reconciliation differ across institutions without a declared policy.

## 3. Decision

### 3.1 OrderConfirmed scope (ACCEPTED baseline)

`OrderConfirmed` triggers two things within ACCSystem:

1. **ACCSystem internal state transition:** The order moves to `CONFIRMED` state. Downstream ACCSystem processes (delivery initiation, notification dispatch, catalog/inventory commit signalling) may proceed.
2. **Delivery initiation:** The delivery workflow is unlocked (subject to delivery provider readiness per ADR-017 policy).

`OrderConfirmed` does **not** assert a universal financial journal posting obligation. The event envelope carries the relevant order, payment reference, and line-item data. What each ACCore does with that data is an institution-local decision.

### 3.2 Financial journal posting (PROPOSED/approval-required)

**The actual ledger entry (financial journal posting) in ACCore is:**
- Triggered by ACCore's local accounting policy
- Owned by the institution's Finance function
- Governed by the institution's jurisdiction, accounting standard, and revenue recognition rules
- Configured in the ACCSystem policy store (ADR-017, ADR-022) as an institution-scoped accounting trigger policy

This decision governs the institution-local ACCore journal only. It does not assign ownership of any future ACCSystem Settlement/Ledger boundary for seller credit, commission payable, settlement finality, or platform immutable postings; that boundary remains PROPOSED/owner-unassigned in `supporting-views/financial-ledger-and-settlement.md` and requires separate Finance/Legal/provider approval.

> [!IMPORTANT]
> **PROPOSED/approval-required:** The specific accounting trigger (which event, which state, at what point) is an institutional authority decision. No production deployment activates financial journal posting without explicit Finance/Legal/Compliance owner approval. The architecture supplies the event and the hook; the institution declares the commitment point.

### 3.3 Event envelope content

The `OrderConfirmed` event envelope MUST carry (at minimum):

| Field | Purpose |
|---|---|
| `order_id` | Stable order reference |
| `seller_order_ids[]` | Per-seller scoped references |
| `payment_reference` | Applicable payment/provider reference(s), preserving per-seller allocations or supported aggregation; exact mapping is open |
| `policy_snapshot_version` | Version of price, tax, commission policy in effect at confirmation |
| `confirmed_at` | Timestamp of saga confirmation commit |
| `line_items[]` | Product, quantity, price, tax lines |
| `institution_id` | ACCore instance scope |

The event does not carry a `journal_entry` instruction field. ACCore constructs its own journal entry according to its local accounting policy.

### 3.4 Interim assumption

Until institutional accounting policy is formally approved and configured:
- ACCSystem records a `PaymentIntent` and all associated records per ADR-016
- ACCore receives `OrderConfirmed` and queues a local accounting task per its institutional policy
- No automated journal entry is created by architectural assumption alone
- Finance owners must explicitly configure the accounting trigger before production capability enablement

## 5. Assumptions

1. ACCore has a configurable accounting trigger that can be set to fire on `OrderConfirmed` receipt, or on a later event (e.g., delivery completion, capture confirmation), per institution.
2. The `policy_snapshot_version` in the event envelope is sufficient for ACCore to reconstruct the policy context at confirmation time.
3. ADR-016 append-only ledger requirements apply to all journal entries, regardless of when they are triggered.
4. Unknown payment outcomes (ADR-006, ADR-013, ADR-018) block `OrderConfirmed`; definitive authorization or approved/supported immediate capture is required according to the selected policy and all other guards.

## 6. Impact and Risks

| Impact / Risk | Severity | Mitigation |
|---|---|---|
| Institutions activate financial trigger without Finance approval | High | External gate: accounting trigger policy requires Finance owner sign-off in onboarding workflow |
| Revenue recognition diverges across institutions without audit trail | High | `policy_snapshot_version` and `confirmed_at` provide reconciliation anchor; ADR-016 immutable ledger applies |
| `OrderConfirmed` is treated as universal commit by an implementer | Medium | Architecture documents (this ADR) explicitly prohibit this assumption; contract tests verify trigger is not hard-wired |
| Delay between OrderConfirmed and ACCore journal posting creates temporary gap | Low–Medium | Acceptable interim; institution's accounting policy defines maximum allowable lag |

## 7. Acceptance Test

1. **OrderConfirmed does not hard-wire ledger commit:** **PLANNED — NOT EXECUTED.** A contract test must assert that emitting `OrderConfirmed` does not automatically create a ledger entry in ACCore in the absence of a configured accounting trigger policy.
2. **Event envelope completeness:** **PLANNED — NOT EXECUTED.** Integration tests must verify that every `OrderConfirmed` event carries all required fields listed in §3.3.
3. **Policy-configured trigger fires correctly:** **PLANNED — NOT EXECUTED.** Tests must cover both an `OrderConfirmed` trigger and a later configured event without premature posting.
4. **Unknown payment blocks OrderConfirmed:** **PLANNED — NOT EXECUTED.** Tests must verify that `payment_state = AUTHORIZATION_UNKNOWN` does not emit `OrderConfirmed`.
5. **Snapshot immutability:** **PLANNED — NOT EXECUTED.** Tests must verify that a later policy version does not alter the snapshot on a previously confirmed event.
