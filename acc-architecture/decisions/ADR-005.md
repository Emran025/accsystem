# ADR-005 — Integration via APIs and Events with Outbox/Inbox and Idempotency

**Decision ID:** ADR-005  
**Status:** PROPOSED  
**Date:** 2026-11-15  
**Evidence:** idea.md §4.3, §14

---

## 1. Problem / Context

ACCSystem and ACCore are separate systems (possibly separate networks, potentially offline). Integration between them must be reliable, recoverable from failures, and idempotent — avoiding duplicate side-effects on retry.

---

## 2. Alternatives Considered

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — Outbox/Inbox + idempotency** (selected) | Each system writes to a local Outbox before sending; receiver writes to Inbox before processing; all operations carry idempotency keys | + Durable local intent and recoverable at-least-once delivery attempts. + Idempotent effects with appropriate safeguards; outages, DLQ and recovery remain operational concerns. — Additional DB tables and polling/CDC infrastructure. |
| **B — Direct synchronous API only** | Systems call each other directly; retry on failure | + Simple. — Tight coupling. — Data loss if crash between send and process. — Impractical if ACCore is offline. |
| **C — Message broker (central)** | Shared message broker between ACCSystem and ACCore | + Decoupled. — Central broker is single point of failure. — All ACCore instances must connect to same broker (network concern). — Complicates per-institution isolation. |

---

## 3. Decision

**All cross-system integration uses the Outbox/Inbox pattern with idempotency keys.**

- **ACCore → ACCSystem (publication):** ACCore writes to its Outbox; CMP-CON-PUBLISHER sends to CMP-INT-GATEWAY; idempotency key: `{institution_id}:{seller_product_id}:{version}`.
- **ACCSystem → ACCore (reservation):** Direct synchronous call (saga path) with idempotency key: `{order_id}:{seller_id}`; ACCore's CMP-CON-RESERVATION is idempotent.
- **ACCSystem → ACCore (order confirmation):** ACCSystem Outbox → Integration dispatcher → ACCore Inbox; receiver business scope is `institution_id + order_id` with role/effect protection as needed; event ID traces redelivery (IF-ACC-ORDER-CONFIRM §2A).
- **Within ACCSystem:** CNT-ACC-EVENTBUS carries events between services; Outbox provides durable intent and recoverable at-least-once attempts, not unconditional consumer completion.

---

## 4. Rationale

- CONFIRMED (idea.md §4.3): Outbox/Inbox pattern described for ACCore integration.
- CONFIRMED (idea.md §14): Idempotency as a cross-cutting concern.
- Pattern handles ACCore offline scenarios gracefully — messages queue in Outbox until ACCSystem is reachable.

---

## 5. Consequences, Risks, Mitigations

| Consequence | Type | Mitigation |
|---|---|---|
| Outbox polling adds latency | Performance | CDC (change-data-capture) reduces latency vs polling; ASSUMPTION: polling for MVP |
| At-least-once delivery = duplicates possible | Correctness risk | Idempotency keys on all handlers eliminate duplicate side-effects |
| Outbox tables require maintenance | Operational | Cleanup uses `policy:outbox.retention_policy`; owner approval and deduplication/reconciliation/audit/legal checks are required before deletion |
| ACCore Inbox must handle concurrent delivery | Concurrency | Inbox record as mutex (PROCESSING status) |
