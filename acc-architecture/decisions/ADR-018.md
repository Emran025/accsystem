# ADR-018 — Reservation State Machine, UNKNOWN Handling, TTL Policy, and Vocabulary Canonicalization

**Decision ID:** ADR-018
**Status:** ACCEPTED (RP-01 contradiction fix); PROPOSED/approval-required (TTL numeric values, async-callback delivery mode per institution)
**Date:** 2026-11-19
**Evidence:** ADR-006 §3.1–§3.2, ADR-013 §4, ADR-015, interface-contracts.md §3.6, idea.md §7.2, §12; open issues RP-01, RP-03

---

## 1. Problem / Context

Two contradictions were discovered in the existing architecture documents:

**RP-01 — UNSAFE timeout handling in interface-contracts.md §3.6:**
The error-cases table for `IF-ACC-RESERVE-SAGA` contained the row:

> "Timeout before response → Saga step marked as uncertain; query status endpoint; **compensate if no confirmation**"

This is **architecturally unsafe**. A timeout is not proof that a reservation request was not received or not acted upon by ACCore. Compensating on timeout alone can cause:
- Double-compensation (releasing a hold that ACCore has already committed)
- Inventory oversell if ACCore accepted and the saga also retried on a new idempotency key
- Financial side effects before state is known

ADR-006 §3.1–§3.2 and ADR-013 §4 both correctly define the UNKNOWN-safe rule but interface-contracts.md §3.6 contradicted them. This ADR resolves the contradiction in favour of the safe rule.

**RP-03 — Vocabulary inconsistency:**
`IF-ACC-RESERVE-SAGA` and `IF-ACR-RESERVATION-RESP` use `ACCEPTED/REJECTED` in their schema examples, but the saga compensation table intermittently used `RESERVED/INSUFFICIENT` language. No canonical set was declared. This creates ambiguity for implementers.

## 2. Alternatives Considered

| Alternative | Description | Trade-offs |
|---|---|---|
| **A — UNKNOWN-hold, query, reconcile (selected)** | Timeout → UNKNOWN on saga state; payment blocked; query ACCore by idempotency key; compensate only on definitive REJECTED/EXPIRED outcome | + Architecturally safe. + Consistent with ADR-006, ADR-013. — Saga may remain in UNKNOWN for a configurable reconciliation window. |
| **B — Compensate on timeout (rejected)** | Treat timeout as failure; release hold immediately; compensate | — UNSAFE: timeout ≠ failure. ACCore may have accepted; compensation releases a live hold or triggers a double-action. |
| **C — Retry indefinitely without state transition** | Never record UNKNOWN; just retry | — No visibility into pending holds. — No reconciliation hook. — Infinite saga stall. |

| Vocabulary option | Description | Trade-offs |
|---|---|---|
| **A — Canonical ACCEPTED / REJECTED / UNKNOWN (selected)** | All reservation interface responses normalized to these three values | + Single source of truth. + Implementer clarity. — Requires mapping note for legacy RESERVED/INSUFFICIENT references. |
| **B — Allow both vocabularies** | Keep RESERVED/INSUFFICIENT and ACCEPTED/REJECTED in parallel | — Ambiguity. — Implementation bugs. |

## 3. Decision

### 3.1 Reservation UNKNOWN-safe state machine rule

**Adopted rule (aligns interface-contracts.md §3.6 with ADR-006 §3.2 and ADR-013 §4):**

| Saga-side event | Required saga action |
|---|---|
| ACCore responds `ACCEPTED` | Mark that reservation `ACCEPTED`; proceed to payment only after all required seller holds are authoritatively accepted and other guards hold |
| ACCore responds `REJECTED` | Mark definitive rejection, block checkout, and compensate eligible confirmed peer effects only under the UNKNOWN guard; retain pending work until relevant outcomes are resolved |
| ACCore responds `UNKNOWN` | Mark reservation `UNKNOWN`; block payment step; query ACCore by `idempotency_key` / `reservation_id`; await definitive `ACCEPTED`, `REJECTED`, or `EXPIRED`; never compensate or release on UNKNOWN alone |
| Timeout before saga receives response | Mark reservation `UNKNOWN` on saga state; block payment step; query ACCore using `idempotency_key`; do not compensate or release until a definitive `ACCEPTED`, `REJECTED`, or `EXPIRED` outcome is confirmed by ACCore query or reconciliation |
| ACCore reports `EXPIRED` (authoritative auto-release) | Record expiry, block confirmation and reconcile in-flight payment/peer outcomes; compensate eligible confirmed effects under guards and close only when required outcomes are resolved |
| Reconciliation window elapsed, still UNKNOWN | Escalate to `PENDING_REVIEW`; alert Operations/SRE; human or automated reconciliation required; no automated compensation |

> [!IMPORTANT]
> **Non-negotiable rule:** A timeout or elapsed wall-clock time alone is **never** proof that a reservation succeeded or failed. UNKNOWN outcomes remain UNKNOWN until reconciliation resolves them. No release, void, or financial side effect may occur before an UNKNOWN outcome is resolved.

### 3.2 TTL policy

The reservation TTL (hold duration before ACCore auto-releases) is **set and enforced by ACCore's local policy**, not asserted in the saga request schema. The `reservation_ttl_seconds` field in `IF-ACC-RESERVE-SAGA` request bodies is a **request hint only**.

> [!WARNING]
> `reservation_ttl_seconds` is a hint, not a contract. The authoritative TTL is ACCore's local policy value. The saga MUST NOT treat elapsed wall-clock time as proof of expiry. Actual numeric TTL values are configurable per institution per ADR-022 and require institutional authority approval before production use. This field is PROPOSED/approval-required.

The saga holds a reservation in its `UNKNOWN` state until one of:
1. ACCore responds definitively (via synchronous retry or query)
2. ACCore notifies `EXPIRED` (authoritative expiry signal from ACCore)
3. Human/automated reconciliation resolves the state

### 3.3 Canonical response vocabulary

**All reservation interface responses (`IF-ACC-RESERVE-SAGA` and `IF-ACR-RESERVATION-RESP`) MUST use:**

| Status token | Meaning |
|---|---|
| `ACCEPTED` | ACCore confirmed the reservation hold is active |
| `REJECTED` | ACCore definitively refused (inventory insufficient, item unavailable, policy block) |
| `UNKNOWN` | ACCore cannot immediately determine outcome; query required |
| `EXPIRED` | ACCore previously accepted but the TTL elapsed and ACCore auto-released |

**Mapping from deprecated vocabulary:**
- `RESERVED` (old) → `ACCEPTED`
- `INSUFFICIENT` (old) → `REJECTED`

This mapping applies to both `IF-ACC-RESERVE-SAGA` (§3) and `IF-ACR-RESERVATION-RESP` (§9) in interface-contracts.md.

### 3.4 Delivery mode

Default: **synchronous response** to reservation request.
Async-callback mode: **available as a configurable option per ADR-015 connectivity configuration** for institutions where outbound-only connectivity or latency constraints make synchronous response impractical.

> [!NOTE]
> Async-callback mode is PROPOSED/approval-required for specific institutions; it must be explicitly activated via institution onboarding policy, not assumed.

## 5. Assumptions

1. ACCore provides a queryable status endpoint keyed by `idempotency_key` and/or `reservation_id`.
2. The saga orchestrator (CMP-ORD-SAGA) persists reservation state durably across restarts.
3. ACCore sends authoritative `EXPIRED` notifications or makes expiry queryable; the saga does not infer expiry from wall-clock time alone.
4. Numeric reconciliation window and retry interval are externalized to the policy configuration store (ADR-022); no production deployment occurs without approved values.
5. `UNKNOWN` responses from ACCore are transient; ACCore guarantees eventual determinism (ACCEPTED, REJECTED, or EXPIRED) within its operational SLA.

## 7. Acceptance Test

1. **Timeout does not trigger compensation:** A saga that sends a reservation request and receives no response within the configured call timeout transitions the saga step to `UNKNOWN`, does NOT send a compensation/release command, and records a query attempt. ✓
2. **ACCore EXPIRED triggers guarded recovery:** Authoritative expiry blocks confirmation; eligible peer compensation proceeds only under applicable guards and closure waits for unresolved outcomes. This is an acceptance scenario, not an executed test.
3. **Vocabulary conformance:** All reservation response payloads in contract tests use only `ACCEPTED`, `REJECTED`, `UNKNOWN`, or `EXPIRED`; any occurrence of `RESERVED` or `INSUFFICIENT` in a response payload causes test failure. ✓
4. **UNKNOWN blocks payment:** A saga step in `UNKNOWN` state cannot advance to the PaymentAuthorization step; the payment step is skipped and the saga enters a waiting/query loop. ✓
5. **Definitive ACCEPTED after UNKNOWN:** When reconciliation returns `ACCEPTED`, the saga does not repeat the reservation effect and proceeds to payment only once every required hold and guard is satisfied.
6. **TTL hint not treated as authoritative:** The saga does not auto-release a reservation when `reservation_ttl_seconds` elapses; it only treats a reservation as `EXPIRED` when ACCore authoritatively signals it. ✓
