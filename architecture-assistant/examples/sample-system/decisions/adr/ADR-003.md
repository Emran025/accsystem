# ADR-003: Keep the shipment API coarse-grained until service boundaries are evidenced

Status: proposed; not accepted. Scope: whether CNT-API should be split into multiple independently deployable microservices. This does not decide whether the browser application and API should remain separate containers; that is a different boundary and does not by itself justify microservices.

## Evidence and unknowns

The sample has one API container with validation, booking orchestration and repository responsibilities (CMP-API-VALIDATION, CMP-API-BOOKING, CMP-API-REPOSITORY). The sample does not provide team ownership, independent release cadence, traffic profiles, per-capability SLOs, data autonomy, consistency needs, CI/CD maturity, production observability, incident/on-call readiness, security segmentation requirements or actual deployment topology. All technology choices are proposals.

## Alternatives and evaluation

1. **Keep one coarse-grained API service with explicit internal modules.** Lowest distribution/operations burden in this evidence-poor illustrative phase; preserves clear code responsibilities. It does not rule out future extraction.
2. **Split into a few independently deployed services now.** Could enable distinct release/scaling/security boundaries, but no such requirement or independently owned bounded context is evidenced. Would introduce network failures, cross-service consistency/testing/operations work with unknown readiness.
3. **Decompose into fine-grained microservices.** Rejected for this phase: no evidence justifies finer boundaries or per-service autonomy; highest distributed and operational cost.

## Proposal and trade-offs

Keep CNT-API as one coarse-grained service while enforcing module boundaries and explicit data ownership. Do not label this final or approved. Before any split, gather capability/team ownership, change/deploy frequency, traffic/SLO evidence, data consistency needs, security boundaries and operational maturity. If a cohesive capability demonstrably needs independent deployment/scaling/isolation and readiness exists, assess an incremental extraction of one candidate service.

Confidence: low-to-medium because the sample is illustrative and key evidence is absent. Reconsider when real source/requirements, separate ownership, independently deployable business capabilities, or a hard scaling/security constraint is documented. A phased modular design is the current low-risk proposal, not a universal prescription.

Affected IDs: CNT-API, CMP-API-VALIDATION, CMP-API-BOOKING, CMP-API-REPOSITORY. Source: sample fixture only.
