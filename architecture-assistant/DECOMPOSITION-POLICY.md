# Decomposition and analysis coverage policy

For every declared scope, maintain a complete inventory of known systems, people, external systems, containers/data stores, ownership, interfaces, dependencies and source evidence. A complete inventory is mandatory; a C3/C4 view is not automatically required for every element. For large estates, partition by portfolio/domain/system/container, retain stable IDs and cross-links, and expose all partial/deferred/blocked areas. A focused view must never be presented as the whole system.

Select C3 detail by documented decision value: business criticality, complexity, security/regulatory boundary, uncertainty, change rate/coupling, independent ownership or implementation planning. Keep a disposition for every container: `SELECTED`, `NOT_SELECTED`, `CONDITIONAL`, `DEFERRED`, `BLOCKED`, or `UNRESOLVED`. For every not-selected/deferred container, record evidence, reason, affected requirement, residual risk, accountable owner (or an explicit owner-assignment action), next step and concrete revisit trigger. A generic phrase such as “standard service” is not a sufficient rationale. Missing follow-up fields keep the decision unresolved.

Within selected C3 scope, enumerate all meaningful components against known behavior, data, interfaces and responsibilities. Do not provide representative-only decompositions while claiming completion. Split along cohesive ownership/responsibility boundaries, not to inflate diagram count; avoid generic catch-all components.

Select C4/code views only for important/complex components where code structure is evidenced and helps a named decision/audience. Record a code-detail decision for every C3 component. Routine code may be on-demand or captured through focused contracts. Important business operations still need function specifications/mappings when actionable behavior matters. Do not invent code, packages, language or signatures. If implementation is unresolved, state the design-level unknown and revisit when evidence exists.

External/out-of-scope entities are not internal children. Data stores may be decomposed through data models/ownership instead of software components, but name the replacement evidence and its scope. Keep `NOT_APPLICABLE` distinct from an accepted waiver. A genuine waiver of a required gate needs explicit authorized stakeholder acceptance with reference/date, scope, residual risk and replacement evidence. AI-generated approval flags or text are not acceptance. See `policies/completeness-policy.md`, `policies/diagram-selection-policy.md` and `policies/architecture-style-selection.md`.
