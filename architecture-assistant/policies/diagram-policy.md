# Diagram Policy

Follow `diagram-selection-policy.md` and create/update a diagram plan before drawing. Always deliver the scoped C1 and C2 baseline; assess C3, C4, system landscape, dynamic and deployment views with explicit selected/not-selected/conditional/unresolved status and rationale. A portfolio with multiple systems needs a landscape view. Add concern-specific diagrams only to answer a named question or address an evidenced risk. Large models must be navigable and partitioned, with complete scope/coverage disclosure rather than one unreadable diagram.

Use repository-supported notation and inspect the renderer first. Title and scope every view, provide a key/legend, label element types/responsibilities, preserve stable IDs and registry-consistent edges, show technology/protocol where relevant, and link detailed records. Validate syntax, render, and review readability when possible. ID/regex validation alone is not diagram validation. If parsing/rendering is unavailable, report `NOT_VERIFIED` and state what was not checked.

## Stage deliverable and final release requirement
A diagram is an actual saved artifact, not the plan, registry, coverage matrix, Mermaid prose in an unrelated document, or a future-work note. Each workflow stage must create or refresh at least one scoped diagram from then-current evidence and checkpoint its path, scope, maturity and validation status. Carry provisional diagrams forward and reconcile them when facts change. For final release, include the actual C1/C2 baseline diagrams and every evidence-selected C3/C4/supporting diagram; provide an index and partition cross-links for large architectures. A selected diagram that is absent, stale, or not reopened and checked is a release finding. Never mark syntax/render/visual verification as passed unless those checks were actually run. If evidence or tooling prevents a required action, show the precise scope, owner/action and status as BLOCKED or NOT_VERIFIED rather than presenting the diagram plan as completion.
