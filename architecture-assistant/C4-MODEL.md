# C4 Model: Project Application

C4 is a hierarchical way to communicate software architecture at different zoom levels. Its core static views are System Context (C1), Container (C2), Component (C3), and Code (C4). Supporting views are System Landscape, Dynamic, and Deployment. The model is notation- and tooling-independent. Follow `policies/diagram-selection-policy.md`: C1 and C2 are this assistant's baseline; C3 and C4 are selected by evidence and decision value rather than mechanically produced for every parent. For most systems, C1 and C2 may be sufficient. Do not confuse the assistant's complete structured inventories with a requirement to draw every possible diagram.

- **C1 — System Context:** one focal software system, the people and external systems directly connected to it, and important interactions. Keep the view understandable to technical and non-technical audiences; avoid low-level implementation detail.
- **C2 — Container:** one software system, containing applications and data stores, with responsibilities, major technology choices and labeled communication protocols. “Container” means a separately running/executing/deployable application or data store, not necessarily a Docker container. Infrastructure topology belongs in Deployment views.
- **C3 — Component:** one selected container, decomposed into meaningful components with responsibilities and relevant implementation/technology detail. Create when the view helps explain complexity, ownership, risk or planned change; record why other containers are not detailed yet.
- **C4 — Code:** code structures within one selected component (e.g. classes, interfaces, functions, objects or data structures). Optional, focused on important/complex components; prefer tooling-generated/on-demand detail for routine or rapidly changing code. Function specifications/catalogs complement but are not C4 diagrams.
- **System Landscape:** a broad map of related systems in an organization/portfolio, especially when multiple systems are in scope. Pair it with focused context diagrams for individual systems as needed.
- **Dynamic:** runtime collaboration for a named use case. Use sparingly for critical or complex interaction/failure behavior, not every operation.
- **Deployment:** instances of systems/containers placed on infrastructure within one named environment. Create when topology, availability, security, scale or operations matter; one diagram per relevant environment. Do not invent infrastructure.

Every diagram has a title/scope, intended audience, legend/key, explicit element types and concise responsibilities, and clear one-way labeled relationships. C2/C3 show technology when known; container interactions identify protocol/technology when known. Unknowns and proposals are labeled. IDs and records remain traceable. Data stores may use a data-architecture view instead of artificial software components. External systems remain opaque unless evidence documents their internals. Validate syntax and render when possible; ID checks alone are not diagram validation. See `policies/diagram-selection-policy.md`, `DECOMPOSITION-POLICY.md`, and `templates/diagram-plan.md`.

Official reference: https://c4model.com/diagrams

## Diagram delivery cadence
C4 defines the view types and appropriate abstraction; the workflow defines when saved views are produced and refreshed. Keep at least one evidence-grounded diagram artifact current at every project stage, explicitly provisional before scope is settled. Final documentation must deliver actual diagram files, not only a selection plan, prose, or coverage table. This cadence does not mean drawing every C4 level: use C1/C2 as the baseline, and select C3/C4/supporting views by their documented value and applicability. For larger scopes, use a landscape/index plus linked, scoped partitions; preserve complete coverage and label deferred or unresolved areas.
