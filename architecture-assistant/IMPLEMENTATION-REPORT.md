# Implementation Report — Architecture Documentation Assistant

## Outcome

Implemented a reusable architecture-documentation assistant package in the `architecture-assistant` directory, including modular agent skills/profiles, a local RAG subsystem, a runnable model-backed tool-calling CLI, scale-aware diagram selection and architecture-style evaluation. Generated project architecture content is kept separately in `examples/sample-system/`; future system documentation should live in a project-specific architecture root. The current workspace had no pre-existing repository/project instructions or architecture framework, so no existing project files were modified.

## Deliverables

- **Operating contract and activation:** `AGENT.md` is authoritative; `SYSTEM-PROMPT.md` provides a reusable activation prompt; `ASSISTANT-SPECIFICATION.md` describes system purpose, data ownership and limits.
- **Workflow and policies:** `WORKFLOW.md` defines staged discovery through validation with entry/exit conditions. `policies/diagram-selection-policy.md` prioritizes C4 and supporting views by decision value, risk and complexity; `policies/architecture-style-selection.md` compares modular monoliths, coarse-grained services and microservices using evidence and operational readiness. Both policies are injected into every runtime session. Other normative policies cover decomposition, traceability, quality, decisions, documentation, scope and error handling.
- **Templates:** `templates/` includes system skeleton, C1/C2/C3/C4, function, interface, data architecture, deployment, cross-cutting, ADR, and validation report templates.
- **Structured contracts:** `schemas/` contains six JSON Schema files for manifest, element, decomposition map, function, interface and decision records.
- **Validation utilities:** `scripts/validate_architecture.py` performs structural and traceability checks and generates reports. Companion scripts validate traceability/references, generate coverage and check diagram ID consistency.
- **Demonstration:** `examples/sample-system/` illustrates a diagram plan, selected C1/C2/C3 views, C4 disposition, supporting views, operation-to-function mappings, function specifications, an external-service exception, a data-store decomposition exception, and an illustrative ADR that defers microservices pending evidence.
- **RAG retrieval:** `rag/indexer.py` chunks Markdown/text/JSON and ranks with BM25; `rag/cli.py` provides index/search with source citations. It is local, offline and dependency-free. `knowledge-base/guides/` contains evidence-handling guidance.
- **Runnable agent:** `agent/runtime.py` implements the OpenAI-compatible Chat Completions tool loop, loads skills, refreshes local RAG and exposes search/read/list/validate/write tools. The default workflow is autonomous; writes are restricted to the configured architecture documentation folder and existing files are backed up before replacement. `agent/manifest.json` routes task skills; three profiles cover architect, reviewer and librarian. The LLM weights/runtime are provided by the configured external model endpoint, not bundled locally. `.env.example` contains placeholders only.
- **Regression tests:** `tests/` contains 29 tests spanning architecture validation, RAG, policy loading, mocked tool calls, path containment, hard-link refusal, autonomous writes, explicit policy denial and backup behavior.

## How it operates and enforces completeness

The assistant works autonomously in one pass: discovery and scale screening, scope/strategy (including architecture-style evaluation where relevant), a plan covering all official C4 view types and supporting concerns, then baseline C1/C2, selected detail, cross-cutting views and validation. C1/C2 are the baseline for each focal system; C3/C4 and supplementary views are selected by evidence and decision value rather than mechanically required for every element. Large scopes receive explicit inventory and partition/coverage dispositions. Routine clarifying questions, stage approvals and per-file approvals are not requested; uncertainty and unresolved inputs are recorded, and independent safe work continues.

Coverage is based on JSON registries rather than Markdown prose. The validator detects duplicate IDs, missing/invalid parent references, missing component or code mappings, unmapped business operations, orphaned elements, undocumented/unapproved exceptions, missing function/component references, missing decision targets, broken local Markdown references, unknown registered IDs in Mermaid diagrams, and a stage marked `PASSED` while decomposition requirements fail. Coverage reports identify missing IDs rather than allowing a percentage to hide omissions. Data-store and external-service exceptions require rationale and replacement documentation.

Function records connect significant operations to their parent system/container/component and documentation. The included function specifications illustrate language-neutral signatures, pre/postconditions, rules, dependencies, effects, errors, and test expectations. Technology choices are represented as proposed ADRs in the example, not asserted as approved decisions; ADR templates require alternatives, constraints, trade-offs, effects, risks, confidence, assumptions, reconsideration triggers, and affected IDs.

## Run the model-backed agent

Set `OPENAI_API_BASE` and `OPENAI_API_KEY` in the environment. Run `python3 agent/runtime.py --system-dir /path/to/architecture-docs --list-models`, then invoke it with an available tool-capable model and an analysis task. The runtime writes documentation autonomously within that configured folder and backs up replaced files. It does not alter source code, production infrastructure or external systems. Model calls can incur provider charges. No actual architecture-generation model invocation occurred during build validation. See `agent/README.md`.

## RAG and agent use

Build a project-specific index with `python3 rag/cli.py index /home/ubuntu/architectures/<system-slug> --output /home/ubuntu/architectures/<system-slug>/.rag/index.json`, then search with `python3 rag/cli.py search '<question>' --index /home/ubuntu/architectures/<system-slug>/.rag/index.json`. Use `agent/runtime.py` to run the model-backed agent, or load the skill files listed in `agent/manifest.json` into another compatible agent host. Retrieved chunks are evidence pointers, not ground truth; inspect sources and cite paths/IDs.

## Limitations and remaining risks

- The included RAG is BM25 lexical retrieval, not semantic embedding search; synonyms and paraphrases can be missed. The runnable agent requires a compatible model endpoint/API key; it does not bundle model weights. The configured sample default (`gpt-6.1-sol`) was available in the implementation environment catalog, but other endpoints must be checked with `--list-models`.
- The validator uses the standard library and enforces hand-coded structural and cross-reference rules; it does **not** run a full JSON Schema validator. The schemas remain useful contracts but are not automatically applied to every registry record.
- The validator confines documentation references to the architecture root and checks interface providers/consumers. The runtime rejects explicit parent traversal and hard-linked files; local retrieval skips symlinked and hard-linked source files. These measures reduce common path risks but are not a complete OS sandbox and do not eliminate filesystem race conditions.
- Mermaid IDs and Markdown links are checked, but Mermaid syntax is not parsed/rendered. Visual correctness, renderer compatibility and diagram/document semantic agreement remain human-review items.
- Responsibility quality, real-world completeness, security, regulatory, performance and operational adequacy require domain review; automated checks cannot certify these.
- The sample is explicitly illustrative. Its approved exceptions are fixture declarations, not real stakeholder acceptance. Its proposed technologies/decisions are not production recommendations.
- No project-specific system was documented because no system description or source repository was present. Unknown requirements remain unknown; no production architecture has been inferred.

## Use for a new system

1. Read `README.md`, `AGENT.md` and `WORKFLOW.md`.
2. Copy the system skeleton under `/home/ubuntu/architectures/<system-slug>/` and populate the manifest/element/decomposition/interface/function/decision registries using `schemas/` as the contract.
3. Start with discovery and scope; mark evidence versus assumptions and unresolved questions. Do not advance past a failed gate.
4. Complete the diagram plan, then populate baseline C1/C2. Select C3/C4 and supporting views by decision value, risk and evidence; record rationale and explicit dispositions for non-selected, conditional or unresolved views. Map important operations to function records.
5. Compare modular monolith, coarse-grained services and microservices when relevant; do not use system size alone to justify microservices. Record evidence, readiness gaps, confidence, trade-offs and the recommendation in an ADR; keep it proposed until accepted. Evaluate cross-cutting categories and link applicable views to stable IDs.
6. Run `python3 /home/ubuntu/architecture-assistant/scripts/validate_architecture.py /home/ubuntu/architectures/<system-slug>` and resolve every blocker. Review all `NOT VERIFIED` checks. Re-run affected gates after changes.
7. Record changes in the system changelog, preserve stable IDs and accepted decisions, and regenerate affected reports.
