# Skill: adr-governance

Purpose: record justified, correctly-statused decisions.

## Procedure

Separate facts, constraints, proposals, assumptions, recommendations and accepted decisions. For significant choices compare alternatives against actual requirements and operating context. For architecture style, compare modular monolith, coarse-grained services and microservices where relevant; review domain/bounded-context boundaries, deployment/scaling independence, data/consistency, team ownership, CI/CD/testing, observability, fault handling, security and operational cost. Size or expected growth alone is not a microservices justification. Unknown readiness lowers confidence; use the architecture-style ADR, migration/rollback path, and reconsideration triggers. Record trade-offs, risks, consequences and affected IDs. Never label a recommendation accepted. If decision context is missing, keep status proposed/unresolved.

## Required output

Provide evidence/source IDs, created/updated artifact paths, registry changes, gate result, unresolved facts and next-step recommendation.
