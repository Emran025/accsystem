# Controlled, resumable workflow

At every stage: inspect evidence; reread the current baseline; make the best-supported decision; create/update records, registry, architecture-consistency ledger and diagram-coverage matrix; validate; record assumptions, contradictions and open questions; write a durable checkpoint; then proceed automatically. Do not pause for routine questions, stage approval or per-file approval. If evidence is incomplete, continue safe work with explicit provisional labels, alternatives, impact, owner/action and trigger. Stop only an action that crosses the architecture-documentation workspace into source-code, production, infrastructure or external-system changes; report unresolved gates honestly. Follow `CONSISTENCY-AND-POLISH-POLICY.md` and `OUTPUT-DEPTH-AND-AMPLIFIER.md` at every stage, with the iterative read-after-write audit at stage 7.

Reopen impacted gates; matrix has a row for every in-scope ID; no unresolved blocker/major conflict is passed; `validate_release_status.py` confirms manifest/Gate 7/report alignment. A consistent BLOCKED result is not a release pass. If limits stop the loop, checkpoint exact findings and mark PARTIAL/BLOCKED. |

At a checkpoint, record stage name/status, evidence reviewed, durable summary, artifacts touched, blockers/unresolved matters and ordered next actions. Call `checkpoint_architecture_stage` at every stage boundary. If interrupted at a tool/step/token limit, retain transcript state and resume at the first incomplete action; never mark a stage complete merely because files were written.

Repair failed checks where evidence permits. After every fix, reread the changed file and all directly affected dependents from disk, then rerun the relevant structural/reference/diagram and cross-artifact checks. A blocked gate does not prevent independent safe work, but it prevents an overall completion claim when critical. Evidence-based `NOT_SELECTED`/`CONDITIONAL` views are acceptable only with rationale, remaining risk, owner/action and revisit trigger. A waiver requires explicit acceptance from an authorized user/stakeholder and documented scope/evidence; the agent cannot approve its own exception. Changes reopen impacted gates.

## Stage-by-stage diagram deliverables
A saved, renderable architecture diagram is a required artifact at every workflow stage, not only a final-stage checklist item. Create a provisional view as soon as source evidence supports one; update it as scope and facts mature. A stage may reuse and revise the current view when that is the right abstraction, but must not substitute prose, a diagram plan, a coverage matrix, or a promise to draw later. Label tentative facts, unknowns, revision/date and scope. If available evidence is too weak to draw responsibly, create the smallest honest scope/boundary view with unknowns, or record a specific BLOCKED/NOT_VERIFIED exception and next action; never fabricate elements.

- Stage 0: produce an initial system-landscape/context sketch from discovered evidence, visibly provisional.
- Stage 1: save the initial scoped context view and the seven-view selection plan.
- Stage 2: deliver and reconcile C1 for each focal system and the landscape view for a multi-system scope.
- Stage 3: deliver and reconcile C2 for each focal system.
- Stage 4: draw C3 only for evidence-selected containers; show disposition and coverage for all other containers.
- Stage 5: draw focused C4 only where code-level evidence and value justify it; function catalogs/contracts are not substitutes for a C4 diagram.
- Stage 6: draw selected deployment/dynamic/concern views for their named questions and scopes.
- Stage 7: reopen the actual saved diagram sources; regenerate/update stale views; reconcile every partition and ID against registries and the coverage matrix; run syntax/parser and render checks where available, then visual review separately. The final package must include the actual diagrams or indexed partitioned diagram set and an index linking each diagram to its stage/view/scope, alongside the plan, coverage matrix, validation evidence and explicit NOT_SELECTED/deferred/blocked dispositions.

If project scale grows, add hierarchy and navigation—portfolio/landscape map, per-system C1/C2, then domain/container/flow partitions with cross-links—instead of omitting diagrams or creating an unreadable omnibus view. C3/C4 remain evidence-selected: do not force all seven C4 view types into every project merely to satisfy a count. Any final-stage change to scope, IDs, a decision or a contract reopens impacted diagrams and gates; read changed diagrams back from disk and rerun affected checks before release.
